# Архитектура FPV Signal Trainer

**Статус документа:** проект архитектуры, Draft  
**Целевая платформа:** Windows 10/11 + Meta Quest 3  
**Основной режим подключения:** проводной Meta Quest Link по USB  
**Основной язык документации:** русский  
**Язык исходного кода и технических идентификаторов:** английский

## 1. Назначение

FPV Signal Trainer — учебное приложение для студентов, изучающих управление беспилотными летательными системами. Программа выводит изображение выбранного симулятора БПЛА на виртуальный монитор перед глазами пользователя в Meta Quest 3 и позволяет преподавателю или студенту моделировать характерные ухудшения аналогового FPV-видеосигнала.

Приложение должно работать на ноутбуке с Windows. Отдельное Android-приложение (APK) для Quest 3 в основной архитектуре не разрабатывается: приложение собирается как Windows PCVR-программа и запускается через Meta Quest Link.

Программа не создаёт радиопомех в эфире и не управляет реальным радиопередатчиком. Все эффекты являются программной визуальной симуляцией.

### 2.1. Почему PCVR через Link

Meta Quest Link переводит гарнитуру в режим PC VR. Windows-приложение получает данные отслеживания гарнитуры через XR runtime и отправляет сформированное VR-изображение в Quest через USB-соединение.

В этой схеме не нужно самостоятельно реализовывать видеопередачу Windows → Android, ADB-транспорт или USB-протокол. Эти задачи относятся к Meta Quest Link.

Приложение FPV Signal Trainer отвечает за:
- захват окна симулятора;
- подготовку изображения;
- наложение OSD;
- обработку изображения эффектами;
- отрисовку виртуального монитора;
- пользовательский интерфейс и сценарии.

Официальная документация Meta:  
- [Use Link for App Development](https://developers.meta.com/vr/documentation/unity/unity-link/)
- [XR Plugin Management for Meta VR](https://developers.meta.com/vr/documentation/unity/unity-xr-plugin/)

### 2.2. Ограничение Passthrough over Link

Meta документирует Passthrough over Link как функцию для разработчиков и ускорения тестирования. Meta отдельно предупреждает, что визуальное качество и производительность по Link могут отличаться от запуска приложения непосредственно на Quest.

Поэтому:
- Passthrough включается в архитектуру как проверяемая возможность.
- До практического испытания нельзя обещать, что он будет доступен и стабилен в постоянной учебной эксплуатации.
- Если Passthrough окажется обязательным, но непригодным для штатного использования через Link, потребуется пересмотреть платформенную архитектуру. Возможный вариант — отдельная нативная версия для Quest с APK.
- До прохождения этой проверки не следует считать вопрос «без APK» окончательно закрытым для всех функций.

Документация Meta:  
[Use Passthrough Over Link](https://developers.meta.com/vr/documentation/unity/unity-passthrough-use-over-link/)

## 3. Контекстная схема

Основной поток данных:

Ноутбук с Windows  
→ симулятор БПЛА  
→ захват выбранного окна  
→ подготовка видеотекстуры  
→ композиция изображения и OSD  
→ GPU-эффекты аналогового канала  
→ виртуальный монитор в VR-сцене  
→ Meta Quest Link по USB  
→ Meta Quest 3.

Обратный поток:
- Quest 3 передаёт положение и ориентацию головы через Link / OpenXR.
- XR-система Windows использует эти данные для стереоскопического рендеринга.
- Положение виртуального монитора рассчитывается относительно позы головы.

Управление:
- студент или преподаватель выбирает источник видео и профиль на панели Windows;
- параметры OSD и помех настраиваются до начала полёта;
- при необходимости пользователь может включать и отключать разрешённые эффекты во время занятия.

## 4. Логические модули

### 4.1. Application Core

Центральный модуль, который запускает и связывает остальные компоненты.

Ответственность:
- жизненный цикл приложения;
- загрузка конфигурации;
- управление состояниями;
- обмен событиями между модулями;
- обработка ошибок;
- корректное завершение работы.

Основные состояния приложения:
1. Initializing — запуск.
2. DeviceCheck — проверка XR runtime и гарнитуры.
3. Ready — приложение готово.
4. SourceSelection — выбор окна симулятора.
5. Streaming — получение и отображение изображения.
6. SignalLost — источник или поток действительно потерян.
7. Recovering — попытка восстановления.
8. Shutdown — завершение.

### 4.2. XR Display

Отвечает за VR-сцену и отображение виртуального монитора.

Функции:
- стереоскопический рендеринг;
- получение позы головы через OpenXR;
- отображение видеоповерхности перед пользователем;
- настройка ширины, высоты и расстояния виртуального экрана;
- настройка вертикального и горизонтального смещения;
- центрирование экрана;
- управление видимостью монитора;
- обработка потери XR-сессии.

Главный режим — head-locked display: виртуальный монитор следует за поворотами и наклонами головы и остаётся перед направлением взгляда.

Геометрия монитора должна быть отделена от видеопотока: смена размера, положения или расстояния не должна перезапускать захват окна.

### 4.3. Passthrough Capability

Изолированный модуль интеграции с Passthrough API.

Он не должен быть жёстко связан с Video Capture или Signal Engine. Это позволит:
- отключать Passthrough без изменения остальных модулей;
- показывать диагностическое сообщение, если функция недоступна;
- позднее заменить реализацию при смене архитектуры.

Passthrough считается экспериментальной возможностью до отдельного испытания на целевой гарнитуре, версии Link и USB-кабеле.

### 4.4. Video Capture

Захватывает изображение выбранного окна Windows.

Основной кандидат — Windows.Graphics.Capture: API позволяет пользователю выбрать окно приложения или дисплей и получать последовательность кадров.

Резервный вариант — Desktop Duplication API, если потребуется захват монитора целиком либо совместимость с определёнными режимами отображения.

Функции:
- системный выбор окна/дисплея;
- запуск и остановка захвата;
- получение кадров;
- контроль изменения разрешения;
- контроль закрытия или недоступности источника;
- обработка ошибок захвата;
- восстановление после потери источника.

Ограничения:
- некоторые защищённые окна и видеоматериалы могут не захватываться;
- поведение минимизированных окон и эксклюзивного полноэкранного режима необходимо испытать;
- захват должен быть проверен на фактически используемых FPV-симуляторах.

Предпочтительный путь передачи кадров в Unity — GPU-текстуры с минимальным количеством копирований между CPU и GPU. При необходимости производительность обеспечивается Windows native plugin на C++/Direct3D 11. Конкретный способ межмодульного обмена текстурами выбирается после прототипа.

Документация:
- [Windows.Graphics.Capture](https://learn.microsoft.com/windows/apps/develop/media-authoring-processing/screen-capture)
- [Desktop Duplication API](https://learn.microsoft.com/windows-hardware/drivers/display/desktop-duplication-api)

### 4.5. Video Pipeline

Подготавливает изображение перед выводом в VR.

Порядок обработки:
1. Получение кадра источника.
2. Проверка актуальности кадра и разрешения.
3. Масштабирование с сохранением пропорций.
4. Композиция изображения с OSD.
5. Передача итоговой текстуры в Signal Engine.
6. Вывод результата на виртуальный монитор.

Видео не должно искусственно задерживаться, замораживаться или пропускать кадры ради имитации радиопомех.

Необходимо учитывать, что реальная задержка всё равно будет складываться из захвата, обработки, рендеринга и передачи через Link. Её нужно измерить, а не считать равной нулю.

### 4.6. OSD Editor

Редактор экранной индикации аналогичного FPV-видеоканала.

Пользователь должен иметь возможность:
- добавлять и удалять поддерживаемые элементы;
- включать и отключать отдельные элементы;
- перемещать элементы по экрану;
- менять размер, цвет и прозрачность;
- выбирать выравнивание;
- сохранять и загружать профили;
- возвращать стандартную конфигурацию.

Предварительный набор элементов:
- TIMER — таймер;
- RSSI — уровень сигнала, если значение задано или поступает из источника;
- VOLTAGE — напряжение, если значение задано или поступает из источника;
- CHANNEL — канал;
- MODE — режим;
- LINK QUALITY — условный показатель качества канала.

В первой версии значения, для которых нет телеметрического источника, должны быть явно обозначены как демонстрационные/симулируемые. Нельзя выдавать вымышленные значения за реальные данные радиосистемы или полётного контроллера.

Для реалистичного аналогового режима OSD компонуется с изображением до применения визуальных помех. Следовательно, эффекты аналогового канала могут затрагивать и OSD.

### 4.7. Analog Signal Engine

Модуль визуальной симуляции аналогового видеоканала. Основная обработка выполняется GPU-шейдерами, чтобы не создавать лишнюю нагрузку на CPU и не копировать кадры без необходимости.

Согласованные эффекты:

| Эффект | Поведение | Настраиваемые параметры |
|---|---|---|
| Помехи и рябь | Аналоговый шум и динамические помехи | Интенсивность, плотность, масштаб, скорость |
| Горизонтальные полосы | Отдельные тонкие и сравнительно редкие полосы | Частота, толщина, контраст, интенсивность |
| Искажение цветов | Изменение цветопередачи | Насыщенность, оттенок, контраст |
| Цветовое расслоение / 3D-эффект | Красный контур смещён в одну сторону, синий — в противоположную | Смещение X/Y, интенсивность, направление |

Требования:
- отдельный переключатель каждого эффекта;
- общий переключатель всех искусственных помех;
- плавная регулировка интенсивности;
- возможность комбинировать эффекты;
- сброс настроек;
- сохранение профилей.

Не входят в план:
- цифровая блочная пикселизация;
- искусственное замирание изображения;
- искусственная потеря кадров;
- искусственная задержка;
- намеренное ухудшение плавности ради имитации потери пакетов.

### 4.8. Реальная потеря изображения

NO SIGNAL — не художественный эффект и не пользовательская помеха.

Он отображается только при подтверждённой потере источника или видеопотока, например:
- выбранное окно закрыто;
- источник захвата завершился с ошибкой;
- Windows сообщил о потере сессии захвата;
- поток кадров перестал обновляться дольше заданного порога.

Нельзя определять потерю сигнала только по чёрному цвету кадра: симулятор может законно показывать чёрное изображение.

Искусственные помехи никогда не должны вызывать NO SIGNAL. После восстановления источника приложение должно автоматически вернуться к нормальному отображению.

### 4.9. Scenario Manager

Управляет наборами параметров Signal Engine и OSD.

Функции первой версии:
- создание профиля;
- изменение параметров;
- сохранение и загрузка;
- запуск профиля;
- сброс к стандартному состоянию.

Позднее можно добавить последовательности событий по времени, случайные изменения интенсивности, учебные задания и журнал занятия. Эти функции не являются обязательными для первого рабочего релиза.

### 4.10. User Interface

Предусматриваются две группы интерфейсов.

**Панель Windows:**
- состояние Quest Link и XR runtime;
- выбор окна симулятора;
- статус источника видео;
- выбор профиля OSD;
- редактор OSD;
- управление эффектами и сценариями;
- диагностика и настройки.

**Интерфейс в VR:**
- виртуальный монитор;
- компактный индикатор подключения;
- минимальные элементы управления, если они потребуются;
- сообщение о реальной потере изображения.

Основную настройку рекомендуется выполнять с ноутбука, чтобы студенту не приходилось снимать гарнитуру или искать мелкие элементы управления в VR.

## 7. Границы ответственности и обмен данными

Модули не должны напрямую изменять внутреннее состояние друг друга.

Предлагаемые контракты:
- Video Capture публикует кадр, параметры источника и события состояния.
- Video Pipeline управляет масштабированием и композицией.
- OSD Editor выдаёт конфигурацию и слой элементов.
- Signal Engine принимает итоговую текстуру и параметры эффектов.
- XR Display получает обработанную текстуру и выводит её на экран.
- Scenario Manager изменяет параметры через публичные интерфейсы.
- Application Core координирует жизненный цикл и ошибки.

Ключевые типы данных:
- VideoSourceInfo — сведения об источнике и разрешении;
- CapturedFrame — кадр и временная метка;
- CaptureStatus — состояние захвата;
- OsdLayout — расположение и настройки элементов OSD;
- SignalEffectSettings — параметры визуальных эффектов;
- ScenarioProfile — сохранённый набор настроек;
- XrDisplaySettings — размер и положение виртуального монитора.

Все структуры конфигурации должны иметь версию схемы, чтобы в будущем можно было безопасно обновлять сохранённые профили.

## 8. Производительность и отказоустойчивость

Основные принципы:
- не кодировать и не передавать отдельный видеопоток в Quest: эту работу выполняет Link;
- не выполнять тяжёлую обработку каждого кадра на CPU без необходимости;
- по возможности держать видеотекстуру на GPU;
- ограничить лишние копирования кадров;
- не создавать искусственную задержку;
- не блокировать XR render loop ожиданием кадра захвата;
- корректно обрабатывать изменение разрешения и потерю устройства;
- отделять технический статус источника от визуальных эффектов.

Нужно измерять:
- частоту кадров захвата;
- частоту VR-рендеринга;
- задержку от захвата до отображения;
- время работы GPU-шейдеров;
- загрузку CPU/GPU;
- стабильность USB Link;
- температуру гарнитуры и ноутбука;
- длительность непрерывной работы.

Численные критерии производительности фиксируются после прототипа на реальном ноутбуке и конкретном кабеле. Не следует обещать задержку или FPS до измерений.

## 9. Тестирование

### Этап A — технический spike

До реализации всего приложения проверить:
1. Meta Quest Link работает по имеющимся A-C и C-C кабелям.
2. USB-тест Meta показывает достаточную и стабильную скорость.
3. Windows PCVR-приложение на Unity/OpenXR запускается в Quest 3.
4. Положение головы корректно поступает в PCVR-приложение.
5. Виртуальная панель может быть закреплена относительно головы.
6. Passthrough over Link доступен и приемлем по качеству, если требуется.
7. Выбранные симуляторы можно захватывать без неприемлемой задержки.

### Этап B — функциональные тесты

- выбор и смена окна источника;
- изменение разрешения источника;
- закрытие симулятора;
- чёрный кадр как штатное содержимое;
- потеря и восстановление захвата;
- включение/отключение каждого эффекта;
- комбинация эффектов;
- настройка и сохранение OSD;
- загрузка сценариев;
- сброс конфигурации.

### Этап C — длительные испытания

Проверить стабильность на протяжении типичного учебного занятия, нагрев, заряд батареи, производительность ноутбука и удобство работы с клавиатурой/мышью.

## 11. Git и процесс командной разработки

Рекомендуемые ветки:
- main — стабильное состояние;
- develop — интеграционная разработка;
- feature/<name> — отдельные функции;
- fix/<name> — исправления.

Правила:
- каждая задача имеет Issue;
- работа над функцией ведётся в отдельной ветке;
- изменения поступают в develop через Pull Request;
- стабильные версии отмечаются Git-тегами;
- alpha/beta выпускаются как GitHub Pre-release;
- README, архитектура и CHANGELOG обновляются вместе с существенными изменениями.

Все участники должны использовать совместимые версии Unity и пакетов, зафиксированные в репозитории.

## 12. Основные риски и критерии принятия решений

| Риск | Почему важен | Что делаем |
|---|---|---|
| Низкая скорость/нестабильность USB | Link может работать с плохим качеством или отключаться | Тест каждого кабеля и порта |
| Passthrough over Link | Это developer-only функция, а не гарантированная производственная функция | Проверка до утверждения финальной архитектуры |
| Задержка | Важна для обучения управлению БПЛА | Замеры полного тракта на реальном оборудовании |
| Захват симулятора | Разные графические режимы могут вести себя по-разному | Проверить все используемые симуляторы |
| Нагрузка на GPU | VR и эффекты работают одновременно с симулятором | GPU-обработка и профилирование |
| Совместимость пакетов | XR SDK и Unity обновляются | Фиксация версий и проверка обновлений |

## 13. Что не входит в первую версию

- беспроводная передача;
- HDMI-карты захвата;
- отдельное Android-приложение для Quest;
- реальные радиопередатчики и радиоподавители;
- подключение к физическому радиоканалу;
- автоматическое чтение телеметрии полётного контроллера;
- искусственная задержка, фризы и потеря кадров;
- цифровая пикселизация;
- многопользовательская система преподавателя;
- облачная инфраструктура.

## 14. Критерий готовности первой версии

Первая версия считается готовой, когда студент может:
1. Подключить Meta Quest 3 к ноутбуку через USB и запустить Link.
2. Запустить FPV Signal Trainer на Windows.
3. Выбрать окно симулятора.
4. Увидеть изображение на виртуальном head-locked мониторе.
5. Настроить положение и размер монитора.
6. Настроить OSD и сохранить профиль.
7. Включать и регулировать аналоговые помехи.
8. Отключать эффекты полностью.
9. Получать NO SIGNAL только при реальной потере источника/потока.
10. Работать без Wi-Fi и без карты захвата.

Passthrough считается отдельным обязательным пунктом приёмки, если техникум подтверждает, что студент должен видеть клавиатуру и физическое рабочее место через гарнитуру. До проверки Meta Quest Link этот пункт имеет статус технического риска.

# Участие в разработке

## Перед началом
1. Прочитайте README.md и документы в docs.
2. Проверьте существующие Issues и Pull Requests.
3. Для новой функции или крупного изменения сначала откройте Issue с целью, ожидаемым поведением и критериями приёмки.
4. Архитектурные изменения предварительно обсуждаются.

## Рабочий процесс
- main — стабильная ветка и основа релизов.
- develop — интеграционная ветка, если она будет создана и принята в рабочий процесс.
- feature/short-description — новая функция.
- fix/short-description — исправление.
- docs/short-description — документация.

Изменения поступают через Pull Request. Не отправляйте напрямую в main без согласованного исключения.

## Требования к Pull Request
- Понятное название и описание.
- Ссылка на Issue, если он есть.
- Тесты либо объяснение, почему они неприменимы.
- Обновление документации при изменении поведения или архитектуры.
- Отсутствие временных файлов, секретов и посторонних бинарных файлов.

## Код и ресурсы
- Имена классов, методов, переменных и комментарии в исходном коде — на английском.
- Документация может быть на русском.
- Следуйте .editorconfig.
- Не добавляйте зависимости без обоснования.
- Не маскируйте ошибки захвата под визуальные эффекты.
- Перед добавлением изображений, шрифтов, аудио, моделей и библиотек проверьте право на распространение и укажите источник/лицензию в THIRD_PARTY_NOTICES.md.

## Unity
- Используйте версию Unity и пакетов, зафиксированную проектом.
- Не коммитьте Library, Temp, Obj, Build и локальные настройки.
- Сохраняйте Unity .meta-файлы.
- Конфликты сцен и Prefab-файлов разрешайте внимательно.

## Проверки
Выполняйте применимые проверки из docs/TEST_PLAN.md. Для XR, захвата и рендеринга указывайте конфигурацию ноутбука, гарнитуры и кабеля.

Соблюдайте CODE_OF_CONDUCT.md.
